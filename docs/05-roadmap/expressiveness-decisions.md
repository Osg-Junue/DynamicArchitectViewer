# 表現力の拡張: 採否の判断記録

分岐シナリオとシーケンス図について、採否と理由をまとめます。

| 機能 | 判断 | 理由 |
| :--- | :--- | :--- |
| 分岐シナリオ（`step` の `scenario` 属性） | 見送り | 試作・プレビュー検証の結果、通常の `step` の並びと状態リセット（`badge: ""`、`color: none`）だけで正常系から障害・フェイルオーバー・復旧まで自然に表現でき（`examples/01-infra-ha-failover.dav`、`examples/05-sequence-payment-retry.dav`）、ドロップダウンによる分岐切り替えは一覧性と DSL の可読性を損なうため |
| シーケンス図（ライフライン形式） | 見送り | 試作・プレビュー検証の結果、ノードを横一列に並べて時間を縦軸に展開すると「構成の塊（グループ・空間配置）を保ったまま状態変化と通信順を再生できる」という本拡張機能の強みが失われるため（現行の `examples/05-sequence-payment-retry.dav` の表現で十分） |

---

## 1. 分岐シナリオを見送った理由（検証結果）

`step "..." [scenario: "正常系"] { ... }` の形式でパーサー・状態解決・再生バー UI を試作し、実プレビューで検証した結果、以下の理由から不採用としました。

1. **`step` だけで十分に表現できる**
   - 既存の `examples/01-infra-ha-failover.dav` や `examples/05-sequence-payment-retry.dav` のように、「正常フロー → 障害発生 → リトライ / フェイルオーバー → 回復・DLQ」を連続した `step` として並べる方が、1 本のストーリーとして追いやすい。
   - 前のステップで付けた `badge` / `color` も、`badge: "", color: none` で任意のステップからリセットできるため、別シナリオを同一ファイル内で続けて書くことも可能。
2. **一覧性と発見しやすさの低下**
   - タイムライン目盛り（`01`, `02`, ...）と `→` キー / `Play all` だけで全ステップを見渡せるのが現行プレイヤーの強みであり、シナリオ選択ドロップダウンに隠すと別経路が見落とされやすい。
3. **DSL の可読性と合流ステップの不自然さ**
   - 1 つのファイル内で複数シナリオの `step` が混在すると、`state` の累積がどのシナリオに効いているか追いにくくなる。
   - 正常系（`200 OK`）と障害系（`402 / 500`）では最終ステップの通知内容や状態自体が異なることが多く、分岐後の共通 `step` に合流する構造が実務の図と噛み合いにくい。

---

## 2. シーケンス図（ライフライン形式）を見送った理由（検証結果）

`examples/05-sequence-payment-retry.dav` をライフライン形式（参加者を横一列に並べ、メッセージを縦方向に積む形式）で描画して現行プレイヤーと比較した結果、以下の理由から不採用としました。

1. **本拡張機能のコアバリュー（構成図×動的ステップ再生）が消える**
   - 静的な作図ツール（Mermaid 等）でシーケンス図が必要なのは、図が動かないため時間を縦軸に展開するしかないからである。
   - 本拡張機能ではすでに `step` と `animate`（`1`, `2`, `3` の順送りバッジとパケット移動）で時系列を表現できており、縦軸にも時間を取ると時間表現が重複する。
2. **空間トポロジと状態変化の見やすさが損なわれる**
   - 全ノードを横一列に並べると、アーキテクチャ上のグループ構造や配置の意味が消え、ノード数が増えるほど横幅と空白ばかりが広がる。
   - ステップごとのノード状態変化（`503` 赤表示、`RETRY` バッジ、途中から出現する `Dead Letter Queue` など）も、縦長の表の上端に固定されて視線移動が大きくなる。
3. **実装・保守コスト**
   - 自動レイアウト・SVG 描画ともに別系統のエンジンが必要となり、「描画実装は 1 つ」「1 人で保守できる規模」の原則に反する。
